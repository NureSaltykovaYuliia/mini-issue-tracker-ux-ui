## 1. Product purpose, actors та межі релізу

### 1.1. Product purpose

> **[SOURCE]** Mini Issue Tracker — внутрішня вебсистема для невеликої команди розробників, призначена для реєстрації, відстеження та координації вирішення проблем програмного продукту. Система має допомагати команді визначати відповідальних, керувати пріоритетами, обговорювати проблеми та швидко знаходити важливі невирішені заявки. Автоматичні рекомендації категорії та пріоритету віднесено до майбутніх вимог, а не до першого релізу.

*Source: §0, Customer Request; §2, Product Vision та Initial Product Scope; §8, MVP / Release Scope.*

### 1.2. Actors та stakeholders

| Actor / stakeholder | Статус у першому релізі | Обґрунтування |
| :--- | :--- | :--- |
| Team Member | Основний користувач | Перегляд, створення заявок, коментарі; зміна статусу лише для призначеної заявки |
| Team Lead | Основний користувач із додатковими правами | Призначення виконавця та встановлення/зміна пріоритету |
| Product Owner / замовник | Secondary stakeholder | Зацікавлений у результатах, але не належить до primary users |
| System Administrator | Secondary stakeholder | Зацікавлений у належній роботі системи, але не є primary user |

*Source: §1, Stakeholders і Primary Users; §3, BR-01, BR-02, BR-06, BR-08.*

> **[SOURCE]** У першій версії передбачено трьох заздалегідь визначених користувачів: двох Team Member та одного Team Lead. Система призначена лише для автентифікованих членів команди.

*Source: §1, Open Questions та відповіді; §3, BR-01.*

> **[UNRESOLVED]** Специфікація не визначає спосіб автентифікації, а §7 прямо зазначає, що його потрібно уточнити. Не можна вважати погодженим конкретний механізм входу, відновлення доступу, реєстрації чи керування обліковими записами.

*Source: §7, R-01; §3, BR-01.*

## 3. Included User Stories та повні Acceptance Criteria

У цьому розділі збережено зміст усіх 33 змістових AC для US-01–US-08. Для US-03 критерії залишаються ненумерованими, оскільки джерело не присвоює їм окремих ID. Gherkin-приклади US-01 є альтернативним поданням критеріїв, а не додатковими AC.

### US-01 — Create Issue

*Source: §5, US-01 — Create Issue.*

> **[SOURCE]** Actor: Team Member.

Мета: створити issue із назвою та описом, щоб зафіксувати проблему та мати змогу відстежувати її.

*Source: §5, формулювання US-01.*

#### Acceptance Criteria

| ID | Тип | Критерій |
| :--- | :--- | :--- |
| AC-01.1 | SOURCE | Користувач може ввести Title та Description. |
| AC-01.2 | SOURCE | Title є обов’язковим. |
| AC-01.3 | SOURCE | Description є обов’язковим. |
| AC-01.4 | SOURCE | Після створення issue отримує ID, status = Open, created_at та author. |
| AC-01.5 | SOURCE | Після створення issue його priority не встановлено. |

*Source: §5, US-01, AC-01.1–AC-01.5.*

#### UI-релевантні висновки

- **[DERIVED]** Форма створення має дозволяти введення Title та Description і перевірку обов’язковості обох значень. Обґрунтування: AC-01.1–AC-01.3.
- **[DERIVED]** У створеної заявки початковий статус — Open, а priority має стан Not Set, а не Low чи Normal. Обґрунтування: AC-01.4–AC-01.5; BR-03–BR-05.
- **[DERIVED]** Успішне створення має бути відрізнене від невдалого, оскільки заявка не повинна вважатися створеною, якщо обов’язкові поля не заповнені. Обґрунтування: AC-01.2–AC-01.3 та Gherkin-приклад порожнього Title у §5.

Джерельні негативні умови: Gherkin-приклад для порожнього Title вимагає не створювати issue та показувати повідомлення Title is required. Це приклад поведінки, пов’язаний із валідацією, а не додатковий AC-ID.

*Source: §5, US-01, Gherkin-сценарій AC-02.*

> **[UNRESOLVED]** Для порожнього Description джерело визначає обов’язковість, але не задає точного тексту повідомлення про помилку.

*Source: §5, AC-01.3; Gherkin-приклад валідації Title.*

### US-02 — View Issues

*Source: §5, US-02 — View Issues.*

> **[SOURCE]** Actor: Team Member.

Мета: переглядати зареєстровані проблеми та їхні поточні деталі.

#### Acceptance Criteria

| ID | Тип | Критерій |
| :--- | :--- | :--- |
| AC-02.1 | SOURCE | Автентифікований член команди може переглянути список зареєстрованих issues. |
| AC-02.2 | SOURCE | Для кожного issue у списку відображаються щонайменше: ID, Title, Status, Priority та Assignee, якщо його призначено. |
| AC-02.3 | SOURCE | Користувач може вибрати issue зі списку та відкрити сторінку його деталей. |
| AC-02.4 | SOURCE | На сторінці деталей відображаються ID, Title, Description, Status, Priority, Assignee, якщо його призначено, Author та Created at. |
| AC-02.5 | SOURCE | Якщо зареєстрованих issues немає, система відображає порожній список або повідомлення про відсутність issues. |

*Source: §5, US-02, AC-02.1–AC-02.5.*

#### UI-релевантні висновки

- **[DERIVED]** Інформаційний склад списку та сторінки деталей різниться: Description, Author та Created at обов’язкові на сторінці деталей, але не в мінімальному переліку полів списку. Обґрунтування: AC-02.2 та AC-02.4.
- **[DERIVED]** Для непризначеної заявки відсутність Assignee є допустимим станом, а не помилкою відображення. Обґрунтування: умовне формулювання Assignee в AC-02.2 та AC-02.4.
- **[DERIVED]** Порожній стан списку є обов’язковим сценарієм. Обґрунтування: AC-02.5.

*Source: §5, US-02, AC-02.2–AC-02.5.*

> **[UNRESOLVED]** Специфікація не визначає сортування, пошук, фільтри, пагінацію або точний формат представлення дати й часу.

*Source: §5, US-02, AC-02.1–AC-02.5; §9 містить лише заголовок.*

### US-03 — Assign Issue to the responsible team member

*Source: §5, US-03 — Assign Issue to the responsible team member.*

> **[SOURCE]** Actor: Team Lead.

Мета: призначити заявку члену команди, щоб визначити відповідального за її виконання.

#### Acceptance Criteria

У джерелі критерії наведено без окремих ідентифікаторів. Їх порядок та зміст збережено.

| Джерельний ID | Тип | Критерій |
| :--- | :--- | :--- |
| Не присвоєно — критерій 1 | SOURCE | Можна вибрати одного assignee. |
| Не присвоєно — критерій 2 | SOURCE | Assignee повинен бути членом команди. |
| Не присвоєно — критерій 3 | SOURCE | Призначати заявку може лише Team Lead. |
| Не присвоєно — критерій 4 | SOURCE | Поточний assignee відображається у заявці. |

*Source: §5, US-03, список Acceptance Criteria 03.*

#### UI-релевантні висновки

- **[DERIVED]** Призначення має підтримувати одного відповідального, а не кількох одночасних виконавців. Обґрунтування: US-03, критерій 1; §1, A-04.
- **[DERIVED]** Вибір виконавця має обмежуватися членами команди. Обґрунтування: US-03, критерій 2.
- **[DERIVED]** Team Member не повинен отримувати доступ до дії призначення як дозволеної операції. Обґрунтування: US-03, критерій 3; §3, BR-01.
- **[DERIVED]** Поточне призначення має бути видимим у заявці після його встановлення. Обґрунтування: US-03, критерій 4.

*Source: §5, US-03; §1, A-04; §3, BR-01.*

> **[UNRESOLVED]** Не визначено, чи дозволено Team Lead знімати призначення, повністю очищати Assignee або перепризначати issue після початкового призначення. Можливість вибрати одного виконавця не визначає всіх правил скасування чи заміни.

*Source: §5, US-03, усі чотири критерії.*

### US-06 — Add Comment

*Source: §5, US-06 — Add Comment.*

> **[SOURCE]** Actor: Team Member.

Мета: додавати коментарі до заявки для обговорення проблеми.

#### Acceptance Criteria

| ID | Тип | Критерій |
| :--- | :--- | :--- |
| AC-06.1 | SOURCE | Текст коментаря не може бути порожнім. |
| AC-06.2 | SOURCE | Доданий коментар зберігається та відображається для відповідного issue. |
| AC-06.3 | SOURCE | Автор коментаря зберігається та відображається. |
| AC-06.4 | SOURCE | Дата й час створення зберігаються та відображаються. |
| AC-06.5 | SOURCE | Якщо збереження не вдалося, коментар не створюється, а система показує помилку. |

*Source: §5, US-06, AC-06.1–AC-06.5.*

#### UI-релевантні висновки

- **[DERIVED]** Коментар повинен бути пов’язаний із відповідною заявкою, а після успішного збереження відображатися разом з автором і датою/часом. Обґрунтування: AC-06.2–AC-06.4.
- **[DERIVED]** Порожній коментар не може бути успішно доданий. Обґрунтування: AC-06.1.
- **[DERIVED]** Помилка збереження не повинна створювати в інтерфейсі враження, що коментар опублікований. Потрібно повідомити про помилку, а сам коментар не має вважатися створеним. Обґрунтування: AC-06.5.
- **[DERIVED]** Успішне відображення тексту в полі введення не є доказом успішного збереження коментаря. Обґрунтування: AC-06.2 та AC-06.5.

*Source: §5, US-06, AC-06.1–AC-06.5.*

> **[UNRESOLVED]** Не визначено, чи можна редагувати або видаляти коментарі, чи є обмеження довжини тексту та як саме користувач може повторити невдале збереження.

*Source: §5, US-06, AC-06.1–AC-06.5.*

| AC-07.3 | SOURCE | Після зміни статусу система зберігає нове значення та відображає його при наступному перегляді заявки. |
| AC-07.4 | SOURCE | Користувач, який не є виконавцем заявки, не може змінити її статус. |
| AC-07.5 | SOURCE | Система не дозволяє встановити значення статусу, якого немає у визначеному переліку. |

*Source: §5, US-07, AC-07.1–AC-07.5.*

#### Обов’язкові правила переходів

> **[SOURCE]** BR-08.1 дозволяє лише такі переходи:

| Поточний статус | Наступний статус | Статус правила |
| :--- | :--- | :--- |
| Open | In Progress | Дозволено |
| In Progress | Resolved | Дозволено |
| Resolved | Closed | Дозволено |
| Resolved | In Progress | Дозволено — повторне відкриття роботи |
| Будь-який інший перехід | Будь-який інший статус | Заборонено |

*Source: §3, BR-08.1.*

#### UI-релевантні висновки

- **[DERIVED]** Можливі дії зміни статусу повинні залежати від поточного статусу, а не просто показувати всі чотири значення як взаємозамінні. Обґрунтування: BR-07–BR-08.1.
- **[DERIVED]** Користувач, який не є призначеним виконавцем, не повинен мати дозволеної дії зміни статусу. Обґрунтування: AC-07.4; BR-08.
- **[DERIVED]** Resolved не можна ототожнювати з Closed. Заявка зі статусом Resolved може перейти до In Progress або Closed, тоді як інші переходи заборонені. Обґрунтування: BR-08.1.
- **[DERIVED]** Новий статус має залишатися актуальним під час наступного перегляду issue. Обґрунтування: AC-07.3.

*Source: §3, BR-07–BR-08.1; §5, US-07, AC-07.1–AC-07.5.*

> **[UNRESOLVED]** Специфікація не визначає точного повідомлення для забороненого переходу, невдалої зміни статусу або втрати прав у момент виконання операції.

*Source: §3, BR-08.1; §5, US-07, AC-07.3–AC-07.5.*

### US-08 — View Important Open Issues

*Source: §5, US-08 — View Important Open Issues.*

> **[SOURCE]** Actor: Team Member.

Мета: швидко бачити важливі відкриті заявки та зосереджуватися на проблемах, що потребують першочергової уваги.

#### Acceptance Criteria

| ID | Тип | Критерій |
| :--- | :--- | :--- |
| AC-08.1 | SOURCE | Issue з priority = High і статусом, відмінним від Closed, відображається у списку Important Issues. |
| AC-08.2 | SOURCE | Issue з priority = Critical і статусом, відмінним від Closed, відображається у списку Important Issues. |
| AC-08.3 | SOURCE | Issues з priority = Low або Normal не відображаються у списку Important Issues. |
| AC-08.4 | SOURCE | Issues зі статусом Closed не відображаються незалежно від priority. |

*Source: §5, US-08, AC-08.1–AC-08.4.*

#### UI-релевантні висновки

- **[DERIVED]** Для включення в Important Issues одночасно потрібні priority High або Critical та status, відмінний від Closed. Обґрунтування: AC-08.1–AC-08.2.
- **[DERIVED]** Статуси Open, In Progress та Resolved відповідають умові «status, відмінний від Closed» за умови priority High або Critical. Обґрунтування: AC-07.2; AC-08.1–AC-08.2.
- **[DERIVED]** Resolved issue з priority High або Critical не можна виключати з Important Issues лише через статус Resolved. Обґрунтування: AC-08.1–AC-08.2 та BR-09.1.
- **[DERIVED]** Low, Normal та Not Set не задовольняють умову включення High/Critical. Для Not Set це логічний висновок із визначеного набору значень, а не окремий пронумерований AC. Обґрунтування: AC-08.1–AC-08.3; BR-04–BR-05.
- **[DERIVED]** Closed issue завжди виключається з Important Issues, навіть якщо його priority Critical. Обґрунтування: AC-08.4.

*Source: §5, US-08, AC-08.1–AC-08.4; §3, BR-04–BR-05 та BR-09.1.*

> **[UNRESOLVED]** Назва US-08 містить слово Open, але критерії включають будь-який статус, відмінний від Closed. Це не можна мовчки змінити на правило «лише Open та In Progress».

*Source: §5, заголовок US-08 та AC-08.1–AC-08.4; §3, BR-09.1.*

### 4.3. Status та переходи

> **[SOURCE]** Допустимі значення status: Open, In Progress, Resolved, Closed.

*Source: §3, BR-07; §5, AC-07.2.*

> **[SOURCE]** Дозволені переходи:
> - Open → In Progress.
> - In Progress → Resolved.
> - Resolved → Closed.
> - Resolved → In Progress — повторне відкриття роботи над issue.
>
> Усі інші переходи заборонені.

*Source: §3, BR-08.1.*

> **[DERIVED]** UI не повинен дозволяти довільний перехід між усіма чотирма статусами. Наприклад, Open → Resolved, Open → Closed, In Progress → Open, Closed → Resolved та Closed → In Progress заборонені заданим правилом переходів.

*Source: §3, BR-08.1.*

> **[UNRESOLVED]** BR-08.1 не визначає дозволеного вихідного переходу зі статусу Closed. За наявним переліком жоден такий перехід не дозволено; підтвердження щодо можливості повторного відкриття Closed issue потребує рішення людини.

*Source: §3, BR-08.1.*

### 4.4. Important Issues

> **[SOURCE]** Issue є важливим за priority High або Critical. Статус Closed виключає заявку зі списку Important Issues незалежно від priority.

*Source: §1, відповідь на питання «Що означає важливі?»; §3, BR-09 та BR-09.1; §5, US-08, AC-08.1–AC-08.4.*

> **[SOURCE]** Resolved означає, що issue вирішено, але ще не закрито. До переходу в Closed заявка залишається активною та може бути в Important Issues відповідно до priority.

*Source: §3, BR-09.1.*

> **[DERIVED]** Для відбору Important Issues потрібно використовувати обидві умови: priority ∈ та status ≠ Closed. Самого priority недостатньо.

*Source: §5, AC-08.1–AC-08.4; §3, BR-09.1.*

### 4.5. Comments

> **[SOURCE]** Текст коментаря не може бути порожнім. Успішно доданий коментар зберігається та відображається для issue разом з автором і датою/часом створення.

*Source: §5, US-06, AC-06.1–AC-06.4.*

> **[SOURCE]** У разі невдалого збереження коментар не створюється, а користувач отримує повідомлення про помилку.

*Source: §5, US-06, AC-06.5.*

> **[DERIVED]** Не можна показувати невдало збережений коментар як опублікований або включати його до підтвердженого переліку коментарів.

*Source: §5, US-06, AC-06.2 та AC-06.5.*

> **[UNRESOLVED]** Не визначено поведінку введеного тексту після помилки збереження: зберігати його в полі, очищати поле чи пропонувати повторну спробу. Також не визначено можливість редагування або видалення коментаря.

*Source: §5, US-06, AC-06.1–AC-06.5.*

### 5.2. Вимоги, які не перевіряються макетом

1. Фактична швидкодія < 1 s. Потрібні технічні вимірювання. Source: §6, NFR-01.

2. Реальна автентифікація та контроль доступу. Візуальний стан кнопки не доводить, що сервер відхиляє заборонені операції. Source: §6, NFR-02; §3, BR-01, BR-06, BR-08.

3. Використання HTTPS. Це характеристика розгортання та мережевого з’єднання. Source: §6, NFR-03.

4. Резервне копіювання всіх даних. Потрібна перевірка інфраструктури та процедури відновлення; конкретна процедура у джерелі не визначена. Source: §8, NFR-04.

5. Фактичне збереження issue і коментарів. Макет може передбачати відображення результату, але не підтверджує збереження даних після повторного запиту. Source: §5, AC-01.4, AC-06.2–AC-06.5, AC-07.3.

6. Заборона недопустимих операцій на рівні системи. Необхідна перевірка поведінки реалізації для ролей і переходів. Source: §3, BR-06, BR-08.1, BR-10; §5, AC-07.4–AC-07.5.

7. Відсутність історії змін як функції продукту. Це питання меж функціональності, а не візуального тестування. Source: §3, BR-11.

### 5.3. Межі NFR-04 та відкладених attachments

> **[SOURCE]** У §6 початковий NFR-04 сформульовано як Backup of all data + attachments, а у §8 оновлену вимогу подано як Backup of all data. Водночас US-09 із файлами перенесено за межі Release MVP.

*Source: §6, NFR-04; §7, рекомендація щодо US-09; §8, Deferred та Updated NFRs.*

> **[UNRESOLVED]** Потрібно підтвердити, чи оновлений NFR-04 повністю замінює початкове формулювання, чи вимога резервного копіювання attachments має залишитися в документації майбутнього релізу. До вирішення цього питання не слід повертати функціональність attachments до MVP.

*Source: §6, NFR-04; §8, NFR-04 та Deferred: US-9.*

## 6. Q-ID — Конфлікти, прогалини та рішення людини

Цей реєстр не змінює вихідних вимог. Кожне питання має бути закрите відповідальною людиною до остаточного погодження відповідної частини UX/UI.

### 6.1. Конфлікти та неоднозначності

Q-01 — Candidate MVP проти остаточного Release Scope

Тип: UNRESOLVED — конфлікт між попереднім плануванням і фінальним scope.

Спостереження: §4 визначає Candidate MVP як SR-01–SR-09, включно з US-09 у детальній специфікації, тоді як §7 рекомендує перенести US-09 за межі першого релізу. §8 остаточно фіксує Release MVP = US-01–US-08, Deferred = US-09.

Висновок для Pack: застосовується §8. US-09 не включається до обов’язкових вимог першого релізу.

Потрібне рішення людини: не потрібне для поточного scope, якщо §8 є затвердженим джерелом Release Scope; потрібне лише в разі наміру змінити межі релізу.

*Source: §4, Candidate MVP; §7, Recommended scope adjustment; §8, MVP / Release Scope.*

Q-02 — Назва Important Open Issues проти правил відбору

Тип: UNRESOLVED — термінологічна неоднозначність.

Спостереження: назва US-08 говорить про відкриті заявки, але AC-08.1 та AC-08.2 включають будь-які статуси, крім Closed. BR-09.1 прямо зазначає, що Resolved issue залишається активним до Closed і може відображатися серед Important Issues.

Висновок для Pack: зберігається точна логіка критеріїв: High/Critical та status ≠ Closed. Resolved не прирівнюється до Closed.

Питання: чи потрібно зберегти назву Important Open Issues як бізнес-термін, чи уточнити назву для відображення фактичної логіки? Це рішення не повинно змінювати AC без погодження.

*Source: §5, US-08, AC-08.1–AC-08.4; §3, BR-09–BR-09.1.*

Q-03 — Початковий priority Not Set та можливість його скасування

Тип: UNRESOLVED — прогалина в правилах життєвого циклу priority.

Спостереження: нове issue має priority Not Set. Після встановлення допустимі Low, Normal, High, Critical. Змінювати priority може лише Team Lead. Правило повернення встановленого priority до Not Set не описане.

Питання: чи дозволено Team Lead очищати встановлений priority?

Висновок для Pack: Not Set є початковим станом, а не п’ятим рівнем priority. Операцію очищення не додавати без рішення людини.

*Source: §3, BR-04–BR-06; §5, US-01, AC-01.5; US-04, AC-04.1–AC-04.2.*

Q-04 — Межі прав на Assignee

Тип: UNRESOLVED — неповна специфікація прав.

Спостереження: Team Lead може призначати issue, можна вибрати одного assignee, який має бути членом команди. Не визначено поведінку очищення призначення, скасування або перепризначення.

Питання: які операції над уже призначеним виконавцем дозволені?

Висновок для Pack: обов’язковими залишаються вибір одного члена команди та відображення поточного assignee. Інші операції не вважаються погодженими.

*Source: §5, US-03, усі чотири ненумеровані критерії; §1, A-04.*

Q-05 — Статус Closed та повторне відкриття

Тип: UNRESOLVED — не повністю визначений життєвий цикл.

Спостереження: BR-08.1 явно дозволяє Resolved → In Progress для повторного відкриття роботи, але не визначає переходу зі Closed до іншого статусу.

Питання: чи є Closed остаточним статусом без повторного відкриття?

Висновок для Pack: не додавати переходи зі Closed до інших статусів. За чинним переліком вони заборонені.

*Source: §3, BR-07–BR-08.1.*

Q-06 — Розбіжність у резервному копіюванні

Тип: UNRESOLVED — відмінність формулювань NFR.

Спостереження: §6 містить Backup of all data + attachments, а §8 — Backup of all data. US-09 відкладено.

Питання: яке формулювання є остаточним для першого релізу та як документувати резервне копіювання attachments для майбутнього релізу?

Висновок для Pack: не трактувати цю розбіжність як підставу включати US-09 до MVP.

*Source: §6, NFR-04; §7, US-09 та R-03; §8, Deferred та Updated NFRs.*

### 6.3. Пропозиції для розгляду — не обов’язкові вимоги

Наведені нижче пункти є PROPOSED і не повинні переноситися в обов’язковий scope без погодження.

- **[PROPOSED]** Погодити каталог повідомлень помилок перед деталізацією взаємодій, оскільки специфікація визначає лише частину точних повідомлень.

Обґрунтування: ці пропозиції спрямовані на уточнення наявних вимог, а не на додавання нових функціональних можливостей.

## 8. Підсумок для наступного етапу

> **[DERIVED]** Pack визначає функціональну основу для подальшого UX/UI-проєктування: доступні операції, поля, стани, переходи, важливі заявки, коментарі, негативні сценарії та технічні обмеження, які не можна підтвердити одним макетом.

*Source: §3, BR-01–BR-12; §5, US-01–US-08 та AC; §6, NFR-01–NFR-04; §8, MVP / Release Scope.*

Перед підготовкою макетів особливо важливо зберегти такі правила:

1. Not Set — це відсутність установленого priority, а не окремий рівень пріоритету.
2. Resolved не дорівнює Closed. Resolved issue з High або Critical може залишатися в Important Issues.
3. Права обмежують дії: Team Lead призначає виконавця та змінює priority; лише призначений виконавець може змінювати status.
4. Недозволені переходи status не можна пропонувати як допустимі дії.
5. Невдале збереження comment не створює опублікованого коментаря та має супроводжуватися помилкою.
6. US-09, SR-10 та SR-11 не належать до обов’язкового функціонального scope першого релізу.
7. Невирішені питання не є погодженими вимогами. Їх не можна самостійно закривати дизайнерськими рішеннями.
