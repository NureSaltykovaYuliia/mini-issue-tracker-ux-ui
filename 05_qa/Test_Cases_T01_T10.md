Статичний макет доводить наявність полів та їхні стани; прототип симулює переходи між екранами. Відповідно до D-08, клікабельний прототип не доводить серверне збереження в БД, авторизацію сесій чи виконання транзакцій.

## Мінітест з одногрупником (§21 методичних рекомендацій)

Тестування проведено 2026-10-23 за участю двох студентів (оператор прототипу — Ходус Данило, незалежний тестувальник — Вдовенко Олег). Завдання виконувалися без усних підказок.

| Завдання | Маршрут учасника | Спостереження, місця вагання та незрозумілі написи |
| :--- | :--- | :--- |
| **1. Створити заявку** | `S-02-A` → клік по кнопці `Create Issue` у правому верхньому куті → відкриття модального вікна `M-01` → візуальний огляд полів Title та Description → клік на `Create` → відкриття екрана деталей `S-03`. | Користувач одразу знайшов кнопку створення. Для скасування операції учасник клікнув на затемнений фон навколо вікна (backdrop) — модалка закрилася без збереження даних; кнопка `Cancel` також доступна. |
| **2. Знайти важливу Resolved-заявку** | `S-02-A` → перемикання на таб `Important` (перехід на `S-02-B`) → знаходження рядка `ISS-101` зі статусом `Resolved` та пріоритетом `High` → клік на назву заявки → перехід до деталей `S-03`. | Перемикання табів зрозуміле. Учасник без вагань визначив, що заявка з пріоритетом `High` зі статусом `Resolved` повинна залишатися у важливих, оскільки вона ще не закрита (`Closed`). |
| **3. Пояснити, чому заданий користувач не може змінити status** | Відкриття екрана деталей `S-03` під контекстом Team Member (non-assignee) або Team Lead (non-assignee) → пошук блоку `Status` → виявлення відсутності активних кнопок. | Учасник зазначив: «Кнопки зміни статусу не активні або відсутні, тому що за правилом бізнес-логіки (AC-07.4 та BR-08) переводити заявку на інший етап може виключно призначений виконавець (current assignee), а не будь-який член команди чи тімлід». |
