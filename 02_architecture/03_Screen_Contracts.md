Mini Issue Tracker — Developer-Verifiable Screen Contracts

Версія: v1.0 APPROVED · База: SD_Spec.docx, Release MVP US-01–US-08, затверджений Decision Log (D-01–D-08) та UX Architecture Plan · Статус: ЗАТВЕРДЖЕНО (Контроль B пройдено)

Цей документ перетворює погоджений за структурою UX-план на перевірювані контракти для розробника й QA. Він не додає продуктових вимог. Якщо джерело не визначає текст помилки, формат дати, спосіб повернення або іншу поведінку, це позначено як невирішене питання чи PROPOSED D-ID, а не як SOURCE.

## 1. Межі та правила читання контрактів

### 1.1. Що входить у Release MVP

| Елемент | Статус |
| :--- | :--- |
| US-01 — Create Issue | SOURCE, MVP |
| US-02 — View Issues | SOURCE, MVP |
| US-03 — Assign Issue to the responsible team member | SOURCE, MVP |
| US-04 — Set Issue Priority | SOURCE, MVP |
| US-05 — Track Issue Progress | SOURCE, MVP |
| US-06 — Add Comment | SOURCE, MVP |
| US-07 — Update Issue Status | SOURCE, MVP |
| US-08 — View Important Open Issues | SOURCE, MVP |
| US-09 — Attach files to an issue | Deferred, не включено |
| SR-10 — Automatic issue categorization | Future, не включено |
| SR-11 — Automatic Priority recommendation | Future, не включено |

Attachments, категоризація, AI-рекомендації, видалення issue та окрема історія змін не повинні з'являтися в макетах чи прототипі як функціональність цього MVP.

### 1.2. Рівні доказу

- Макет — можна перевірити наявність поля, підпису, стану, умовного відображення та доступність елемента у відповідному візуальному варіанті. Макет не доводить, що дані зберігаються.

- Прототип — можна перевірити кліки, перемикання демонстраційних станів, відкриття/закриття модального вікна та передбачені сценарії взаємодії. Прототип не доводить серверні дозволи, персистентність або реальну перевірку даних.

- Реалізація — перевіряються збереження, авторизація, серверні правила, справжні переходи станів, відповіді на помилки та результат після повторного завантаження.

Не можна ставити PASS за майбутній макет або непідключений прототип, якщо критерій вимагає збереження даних, перевірки прав або фактичного результату на сервері.

### 1.3. Позначення

- SOURCE — безпосередньо підтверджено вихідним документом або правилом.

- PROPOSED D-ID — запропоноване UX-рішення, яке ще потрібно погодити.

- UNRESOLVED Q-ID — бізнес-рішення, якого недостатньо у джерелі.

- Annotation — пояснення для дизайну/розробки, а не нова функція.

### 1.4. Інвентар поверхонь

| ID | Тип | Призначення |
| :--- | :--- | :--- |
| S-01 | Auth boundary placeholder | Позначає межу автентифікації; це не готовий екран входу |
| S-02-A | State S-02 | Список усіх зареєстрованих issues |
| S-02-B | State S-02 | Список Important за визначеним predicate |
| S-02-C | State S-02 | Порожній список |
| M-01 | Modal/overlay | Створення issue |

Отже, інвентар містить 3 screen-level surfaces, 3 стани списку, з яких один є empty state, та 1 modal. Стани S-02-A/B/C не є трьома окремими продуктовими сторінками. Assignment, Priority, Status і Comments — області/контроли на S-03, а не окремі екрани.

## 2. Screen contract: S-01 — Authentication boundary placeholder

Призначення: зафіксувати, що доступ до основної системи дозволений лише автентифікованим членам команди. Реальна сторінка входу та спосіб автентифікації не визначені цим UX-планом.

- Actors: автентифікований Team Member або Team Lead; неавтентифікований користувач — лише як контекст блокування доступу.

- Entry conditions: користувач відкриває систему або намагається перейти до захищеної поверхні.

- Source: BR-01, NFR-02; спосіб автентифікації позначений як ризик R-01.

### 2.1. Visible data

| Поле / annotation | Обов'язковість | Відображення відсутнього значення | Джерело |
| :--- | :--- | :--- | :--- |
| Auth boundary annotation | Обов'язковий елемент документації/прототипу | Не застосовується | Annotation, не продуктове поле |
| Login form / username / password | Не визначено | Не визначено | Q-07 / R-01 |

### 2.2. Controls

| C-ID | Label | Type | Visible / enabled | Trigger → результат | Source / D-ID |
| :--- | :--- | :--- | :--- | :--- | :--- |
| C-01-01 | Немає продуктової кнопки у placeholder | Annotation | Видимий лише у специфікації/прототипній позначці | Позначає межу; не імітує успішний login | Annotation |
| C-01-02 | Вхід до захищеної системи | Навігаційна межа | Доступ до S-02 лише після автентифікації | Успішна автентифікація → S-02; конкретний механізм не задано | BR-01; цільова сторінка залежить від T-01 |

### 2.3. Default, empty, validation, error

- Default: placeholder, що пояснює межу автентифікації, без вигаданих полів входу.

- Empty: не застосовується.

- Validation: не визначена, бо поля/метод входу не визначені.

- Error: тексти та вигляд помилок автентифікації не визначені.

- Не можна додавати без рішення: форму з email/password, SSO, кнопку реєстрації, відновлення пароля, demo credentials або вигадану помилку входу.

### 2.4. Transitions

| T-ID | From → To | Умова | Видимий результат |
| :--- | :--- | :--- | :--- |
| T-01 | S-01 → S-02-A або S-02-C | Автентифікацію успішно підтверджено; стартовий стан списку потребує уточнення | Користувач бачить список |
| T-02 | Захищена поверхня → S-01 boundary | Спроба доступу без автентифікації | Доступ до захищених даних не надається; конкретний UI не визначений |

### 2.5. Що перевіряється

- Макет: відсутність вигаданої login-форми.

- Прототип: межа позначена, але не симулює реальну автентифікацію як підтверджений факт.

- Реалізація: автентифікований доступ і блокування неавторизованого доступу. Перевірка потребує тестів реалізації; макет її не доводить.

## 3. Screen contract: S-02 — Issues List

Призначення: переглядати зареєстровані issues і відкривати їхні деталі.

- Actors: Team Member, Team Lead.

- Entry conditions: автентифікований член команди; перехід зі S-01 або повернення зі S-03 за окремо погодженим правилом.

- Source: US-02 / AC-02.1–AC-02.5, US-05 / AC-05.1 та AC-05.3, US-08 / AC-08.1–AC-08.4.

### 3.1. Visible data

| Поле | Обов'язковість | Відсутнє значення | Source |
| :--- | :--- | :--- | :--- |
| Issue ID | Обов'язкове для кожного запису | Не допускається як коректний запис у списку | AC-02.2 |
| Title | Обов'язкове для кожного запису | Не визначено окремий fallback; title є обов'язковим при створенні | AC-01.2, AC-02.2 |
| Status | Обов'язкове для кожного запису | Не допускається як коректний статус; допустимі значення — BR-07 | AC-02.2, AC-05.1, BR-07 |
| Priority | Поле відображається; значення може бути відсутнім | Відображати як Not Set або порожнє значення — формат потребує рішення | AC-02.2, BR-04, BR-05, Q-03 |
| Assignee | Умовне: якщо призначений | Якщо не призначений, показувати відсутність призначення; точний текст/UI — PROPOSED | AC-02.2, US-03 |
| Issue count / лічильник | Не визначено | Не застосовується | Не додавати без рішення |

PROPOSED D-01: для порожнього priority показувати Not Set у списку й деталях. Це лише запропоноване представлення; бізнес-семантика поля як невстановленого значення вже є SOURCE (BR-04/BR-05).

PROPOSED D-02: для issue без assignee показувати Unassigned. Сам факт, що assignee може бути відсутнім, підтверджений AC-02.2; конкретний напис — ні.

### 3.2. Controls

| C-ID | Label | Type | Visible / enabled conditions | Trigger → результат | Source / D-ID |
| :--- | :--- | :--- | :--- | :--- | :--- |
| C-02-01 | All | Tab/filter | Видимий для автентифікованих користувачів | Вибір → S-02-A, усі зареєстровані issues | S-02-A — структура плану; точний tab UI — PROPOSED D-03 |
| C-02-02 | Important | Tab/filter | Видимий для автентифікованих користувачів | Вибір → S-02-B, застосувати Important predicate | US-08 / AC-08.1–AC-08.4 |
| C-02-03 | Issue row/card | Selectable item | Для кожного issue у списку | Вибір issue → S-03 з його даними | AC-02.3 |
| C-02-04 | Create issue | Button | Видимий для автентифікованих членів команди | Натискання → відкрити M-01 | BR-02; місце й вигляд кнопки — PROPOSED D-03 |
| C-02-05 | Back to list | Navigation control | Лише якщо його буде передбачено на S-03 | Повернення до попереднього стану списку | PROPOSED D-04; не погоджено |

### 3.3. State S-02-A — All

Visible data: ID, Title, Status, Priority, Assignee за наявності.

Predicate: усі зареєстровані issues. Жоден додатковий фільтр не визначений.

- Default: список завантажений; початковий стан після автентифікації ще не остаточно визначений.

- Empty: якщо issue немає, показувати S-02-C.

- Validation: не застосовується до перегляду.

- Error: помилка завантаження списку має бути відрізнена від порожнього результату; точний текст і вигляд не визначені (Q-08).

### 3.4. State S-02-B — Important

Точний predicate:

\[

\text{Important}(issue) =

(\text{priority} \in \{\text{High}, \text{Critical}\})

\land

(\text{status} \ne \text{Closed})

\]

Це означає, що Resolved не виключає issue з Important. Issue залишається активним до переходу в Closed (BR-09.1).

| Priority | Status | Включити в Important? | Підстава |
| :--- | :--- | :--- | :--- |
| High | Resolved | Так | High і status ≠ Closed |
| Critical | Closed | Ні | Closed виключається незалежно від priority |
| Відсутній / Not Set | Open | Ні | Відсутній priority не належить до множини High/Critical |
| Low | Open | Ні | AC-08.3 |
| Normal | In Progress | Ні | AC-08.3 |
| Critical | In Progress | Так | AC-08.2 |

- Default: predicate застосовано до поточного набору issues.

- Empty: якщо жодне issue не відповідає predicate, показати S-02-C у контексті Important.

- Validation: не застосовується.

- Error: помилка отримання даних — не тотожна порожньому результату; UI-поведінка потребує рішення Q-08.

### 3.5. State S-02-C — Empty list

Призначення: показати, що в поточному контексті немає записів.

- Source: AC-02.5 прямо дозволяє порожній список або повідомлення про відсутність issues.

- Важливе розрізнення: All empty означає, що issues не зареєстровано; Important empty означає, що немає issues, які відповідають predicate.

- PROPOSED D-05: у порожньому All показувати дію Create issue; у порожньому Important — повідомлення про відсутність важливих issues та спосіб повернутися до All. Обидва конкретні UI-рішення треба погодити.

- Error: мережеву/серверну помилку не можна показувати як звичайний empty state.

### 3.6. Transitions для S-02

| T-ID | From → To | Actor / trigger | Preconditions | Видимий результат |
| :--- | :--- | :--- | :--- | :--- |
| T-01 | S-01 → S-02-A/C | Автентифікований користувач входить | Автентифікацію підтверджено | Список у початковому стані, що ще потребує рішення |
| T-03 | S-02-A → S-02-B | Будь-який Team Member/Lead, натискає Important | Автентифікований | Список відфільтровано за predicate |
| T-04 | S-02-B → S-02-A | Користувач натискає All | Автентифікований | Показано всі issues |
| T-05 | S-02-A/B → S-02-C | Завантаження списку повернуло нуль записів для поточного predicate | Завантаження завершене успішно | Empty state відповідного контексту |
| T-06 | S-02-A/B → S-03 | Користувач вибирає issue | Issue доступний у списку | Відкрито деталі вибраного issue |
| T-07 | S-02-A/C → M-01 | Користувач натискає Create issue | Автентифікований | Відкрито форму створення |
| T-08 | M-01 → S-02-A/C | Користувач скасовує створення | Issue не створено | Повернення до початкового контексту — PROPOSED D-06 |

### 3.7. Що перевіряється

- Макет: наявність потрібних полів, станів All/Important/Empty, візуальне відображення відсутнього priority/assignee.

- Прототип: перемикання All/Important, відкриття деталей, показ empty state для заздалегідь підготовлених прикладів.

- Реалізація: фактичні дані зі сховища, відповідність полів AC-02.2, правильна фільтрація Important, розрізнення empty/error, збереження вибраного контексту при поверненні, якщо таке рішення буде погоджене.

## 4. Screen contract: M-01 — Create Issue modal

Призначення: створити issue з Title та Description.

- Actors: будь-який автентифікований Team Member або Team Lead.

- Entry conditions: відкрито зі списку; користувач має право створювати issue за BR-02.

- Source: US-01 / AC-01.1–AC-01.5, BR-02–BR-04.

### 4.1. User-entered fields vs. automatically assigned data

| Поле | Хто задає | Обов'язковість | Поведінка відсутнього значення | Source |
| :--- | :--- | :--- | :--- | :--- |
| Title | Користувач | Так | Створення заборонене; показати Title is required | AC-01.1, AC-01.2 |
| Description | Користувач | Так | Створення заборонене; точний текст помилки не визначено | AC-01.1, AC-01.3 |
| ID | Система | Автоматично після успішного створення | До створення не показується як готовий ID | AC-01.4 |
| Status | Система | Автоматично | Початкове значення Open | AC-01.4, BR-03 |
| created_at | Система | Автоматично | До створення не заданий | AC-01.4 |
| Author | Система з поточного користувача | Автоматично | Має відповідати користувачу, який створив issue | AC-01.4 |
| Priority | Система | Автоматично у стані Not Set | Не встановлено; це не одне з чотирьох встановлюваних значень | AC-01.5, BR-04, BR-05 |
| Assignee | Не вводиться у формі створення | Не задано вимогу призначати під час створення | Відсутній до окремого призначення | BR-02–BR-06; конкретна відсутність поля — узгоджена структура UX-плану |

### 4.2. Controls

| C-ID | Label | Type | Visible / enabled conditions | Trigger → результат | Source / D-ID |
| :--- | :--- | :--- | :--- | :--- | :--- |
| C-M01-01 | Title | Text input | Видимий при відкритті модального вікна | Введення → значення Title | AC-01.1 |
| C-M01-02 | Description | Text area | Видимий при відкритті модального вікна | Введення → значення Description | AC-01.1 |
| C-M01-03 | Create | Submit button | Видимий; активність кнопки до валідації не визначена | Натискання → перевірка обов'язкових полів; якщо валідні, створити issue | AC-01.2–AC-01.5 |
| C-M01-04 | Cancel | Button | Видимий у модальному вікні | Натискання → закрити modal без створення | PROPOSED D-06 |
| C-M01-05 | Close (×) | Modal close control | Не визначено | Поведінка закриття без створення потребує рішення | PROPOSED D-06 |

### 4.3. Default, empty, validation, error

- Default: Title і Description порожні; поля призначені для введення користувачем.

- Title empty: створення не відбувається; показати точний текст Title is required (AC-01.2 та BDD-сценарій US-01).

- Description empty: створення не відбувається (AC-01.3); точний текст, місце й стиль помилки не визначені — Q-08.

- Successful submit: створюється issue; система задає ID, status = Open, created_at, author, priority = Not Set.

- Failed save: точна поведінка помилки створення не описана в AC; не вигадувати повідомлення або retry UI без рішення.

- Після успіху: відкрити S-03 для нового issue — це було частиною попереднього UX-плану, але є навігаційним рішенням, яке слід підтвердити як PROPOSED D-07, якщо воно ще не погоджене.

### 5.3. Assignment area

- Дозволений actor: тільки Team Lead.

- Дозволений вибір: рівно один assignee; він має бути членом команди (US-03, ненумеровані AC).

- Visible result: поточний assignee відображається в деталях і у списку.

- Team Member: не може призначати issue.

- Team Lead не є assignee автоматично: роль Team Lead сама по собі не дає права змінювати статус.

- Невирішене: чи можна скасувати призначення, повторно призначити іншому члену команди, і як показувати список доступних членів команди (Q-04). Не додавати unassign/reassign UX як остаточне рішення до уточнення.

### 5.4. Priority area

Розрізняти два поняття:

1. Поточне значення priority — може бути відсутнім (Not Set).

2. Дозволені значення для встановлення/зміни — Low, Normal, High, Critical.

Not Set — це стан відсутнього значення, а не п'ятий пріоритет у селекторі. Для новоствореного issue priority не встановлюється автоматично (BR-04).

- Дозволений actor: Team Lead.

- Недозволений actor: Team Member, незалежно від того, чи є він assignee.

- Visible result після успіху: новий priority показано в S-03; у S-02 оновлений priority має бути відображений при наступному перегляді.

- Error state: точний текст і спосіб відновлення після невдалого збереження не визначені (Q-08).

- Невирішене: чи дозволено повертати встановлений priority у Not Set. BR-05 описує дозволені встановлені значення й допускає пусте значення до встановлення; правило скидання після встановлення явно не задано (Q-03).

### 5.5. Status area

- Поточні значення: Open, In Progress, Resolved, Closed.

- Дозволені переходи: лише BR-08.1; див. повну матрицю в розділі 7.

- Дозволений actor: тільки assignee.

- Team Lead non-assignee: не може змінювати статус, попри роль Team Lead.

- Відображення: статус видимий на S-03 та у S-02.

- Error state: недозволена зміна не змінює збережений статус; точний текст помилки не визначено.

- Closed: не має вихідних переходів.

- Невирішене: чи потрібен окремий disabled control або відсутність контролу для недоступних переходів. Це UX-рішення, а не додаткове правило переходу.

### 5.6. Comments area

- Actors: усі чотири actor/context комбінації можуть переглядати деталі як автентифіковані члени команди; додавання коментарів визначене як дія члена команди.

- Валідація: comment text не може бути порожнім (AC-06.1).

- Успішне збереження: comment збережений і показаний у контексті issue (AC-06.2); показані author (AC-06.3) і дата/час створення (AC-06.4).

- Невдале збереження: помилка показана; comment не створюється (AC-06.5).

- Після помилки: чи зберігається текст у полі, чи очищується, не визначено (Q-12). Не фіксувати це як SOURCE.

- Порядок коментарів, пагінація, редагування/видалення коментарів не задані; не додавати до контракту як вимоги.

## 7. Повна матриця переходів статусу

| # | Поточний status | Новий status | Примітка |
| :--- | :--- | :--- | :--- |
| 1 | Open | In Progress | Початок роботи |
| 2 | In Progress | Resolved | Проблему вирішено |
| 3 | Resolved | Closed | Закриття issue |
| 4 | Resolved | In Progress | Повторне відкриття роботи |

Поточний статус — це не перехід. Closed не має вихідних переходів. Не можна додавати переходи з Open безпосередньо до Resolved або Closed, а також з In Progress назад до Open.

### 7.3. Що перевіряється за рівнями

- Макет: візуально представлені тільки допустимі наступні дії; Closed не показує доступного вихідного переходу, якщо обрано відповідний варіант дизайну.

## 10. Тестування проти SOURCE і запропонованого UI

### 10.1. Правило доказу

Кожний тест повинен мати чотири незалежні елементи:

1. Actor/context — хто діє та яке його відношення до issue.

2. Precondition — початкові дані, роль, статус, фільтр і стан UI.

3. Action — точна дія користувача.

4. Expected visible result — що користувач бачить після дії або помилки.

5. Not proven — що не можна вважати підтвердженим цим тестом.

Наприклад, ST-01 доводить дозволений перехід лише тоді, коли реалізаційний тест підтверджує, що після збереження Open змінився на In Progress і це значення відображається при повторному відкритті issue. Клік по кнопці в Figma доводить лише зв'язок між двома прототипними станами.

### 10.2. Не ставити PASS до появи доказу

| Verification level | Допустимий статус до перевірки | Що потрібно для PASS |
| :--- | :--- | :--- |
| Макет | NOT RUN | Відкритий макет із перевіреними полями/станами та зафіксованим результатом |
| Прототип | NOT RUN | Програний сценарій з правильним видимим результатом |
| Реалізація | NOT RUN | Виконаний тест реалізації з фактичним результатом, включно зі збереженням/відмовою |
| Рішення D-ID | PENDING DECISION | Підтвердження відповідальним за продукт; до цього не маркувати як SOURCE |

### 10.3. Контроль покриття

- Усі 33 content acceptance criteria для US-01–US-08 мають рядки в traceability.

- Чотири ненумеровані пункти US-03 включені окремо.

- Перевірки дозволених і заборонених переходів покриті ST-01–ST-14.

- Permission matrix покрита PERM-01–PERM-09.

- Create — CR-01–CR-07; list/details — LS-01–LS-06; assignment — AS-01–AS-03; priority — PR-01–PR-05; Important — IM-01–IM-06; comments — CM-01–CM-06.

Це план тестів, а не звіт про виконання: результати всіх тестів зараз NOT RUN, доки відповідний макет, прототип або реалізацію не перевірено.

| D-03 | Початковий стан списку та розташування дій | Список має підтримувати All і Important | Початковий таб після входу; точне розташування Create і фільтрів |
| D-04 | Повернення зі S-03 до списку | Повернення до списку потрібне для навігації; збереження вихідного стану було запропоновано | Чи повертати до попереднього All/Important та чи зберігати scroll/позицію |
| D-05 | Empty-state CTA | AC-02.5 дозволяє порожній список або повідомлення | Чи показувати Create у порожньому All і яку дію пропонувати в порожньому Important |
| D-06 | Закриття M-01 | Скасування не повинно створювати issue | Чи є Cancel, хрестик закриття та чи повертається користувач у той самий стан списку |
| D-07 | Після успішного Create | Issue створюється з автоматичними значеннями | Чи відкривати S-03 відразу, чи повертати до списку |
| D-08 | Контроли недоступних дій | Заборонені дії не повинні змінювати дані | Приховувати, блокувати чи показувати контроль з повідомленням; серверна заборона потрібна незалежно від вигляду |

### 11.1. Що не можна закривати лише UX-рішенням

Деякі питання є не просто вибором дизайну:

- Q-03: скидання priority змінює бізнес-поведінку, тому потрібне рішення продукту.

- Q-04: правила зміни assignee впливають на відповідальність за issue.

- Q-05: відкриття Closed суперечило б поточній матриці BR-08.1.

- Q-07: реальний механізм автентифікації впливає на безпеку та реалізацію.

- Q-15: NFR не можна підтвердити візуальним макетом.

## 12. Непокриті або не доведені цим контрактом критерії

Усі AC US-01–US-08 відображені в traceability, але це не означає, що кожна пов'язана властивість уже має достатньо деталей для повної реалізації.

| Вимога / правило | Поточний статус | Що ще потрібно |
| :--- | :--- | :--- |
| NFR-01: response time < 1 s | Є в джерелі, але не має завершеного test protocol | Уточнити точку вимірювання, операцію, середовище та метод заміру |
| NFR-02: authentication required | SOURCE; S-01 лише placeholder | Визначити механізм автентифікації й перевірити його реалізацію |
| NFR-03: HTTPS only | SOURCE | Перевірити конфігурацію та доступ по HTTPS; макет не є доказом |
| NFR-04: backup of all data | SOURCE | Визначити/перевірити механізм backup та відновлення; screen contracts цього не доводять |
| Error handling для Create | Частково визначено | Визначено лише точний Title error; інші повідомлення — Q-08 |
| Помилки assignment/priority/status | Правила дозволів визначені, але presentation помилки ні | Уточнити Q-08/D-08; перевірити server-side denial |
| Доступність конкретних issue | Авторизовані члени команди можуть переглядати список і деталі; складніші правила доступу не визначені | Не вигадувати додаткові обмеження видимості |
| Дата/час | Поля обов'язкові до показу | Вирішити Q-09 |
| Збереження попереднього фільтра | Було запропоновано, але не погоджено | Закрити D-04 |
| Поведінка після невдалого comment save | Помилка та відсутність нового comment визначені | Закрити Q-12 щодо введеного тексту |
| Стартовий стан після автентифікації | Не визначено однозначно | Закрити D-03 |
| Поведінка при помилці завантаження списку | Не тотожна empty state, але конкретний UI не визначений | Закрити Q-08 |
| Порядок і пагінація comments | Не визначені | Не додавати без окремої вимоги |
| Unassign / reassign | Не визначені | Закрити Q-04 |
| Reset priority to Not Set | Не визначено після первинного встановлення | Закрити Q-03 |

Важливе розмежування: US-09 attachments, SR-10 categorization та SR-11 priority recommendation — не непокриті критерії цього MVP, а явно виключені з поточного Release Scope. Їх не слід включати в acceptance-тести цього документа.

## 14. Підсумковий контрактний принцип

Для кожної дії має бути однозначний ланцюжок:

Actor + precondition → C-ID → trigger → дозволена зміна даних або відмова → видимий результат → Test ID → verification level.

Якщо будь-якої ланки бракує, розробник не повинен домислювати продуктові правила. Відсутні деталі потрібно залишити як UNRESOLVED Q-ID або запропонувати окремим PROPOSED D-ID, а після рішення оновити контракт і traceability.
